# Vertical slice pilot, October 2026

Pilot acceptance of the vertical slice ([design](superpowers/specs/2026-10-21-framework-design-guidelines-design.md)
§7, [plan](superpowers/plans/2026-10-21-framework-design-guidelines-vertical-slice.md) Task 12), run on 2026-10-23

## Pilot project

An internal WPF/.NET Framework 4.7.2 repository with 92 C# projects:

- `src/`: 24 SDK-style projects, all onboarded with profile `application`;
- `tests/`: 29 SDK-style projects, all onboarded with profile `test`;
- `<legacy-root>/`: older code, deliberately not onboarded: 33 SDK-style and 2 legacy (non-SDK) projects;
- `Tools/`: 3 legacy projects; `samples/`: 1 SDK-style project, not onboarded.

The main solution is `<legacy-root>/App.slnx`. It contains every onboarded project except one, `src/App.Host`. The
repository already used central package management and had its own `tests/Directory.Build.props`. Code is C# 7.3.

Placeholders used below: `<pilot-dir>` is the pilot working directory, `<pilot-repo>` the clone, `<fdg-repo>` this
repository. Project and file names from the pilot repository are replaced by `App.*`, `Lib.*` and similar names.

### 1–5: `/fdg-setup` (Claude)

(src/** application, tests/** test, no library, no PublicApiAnalyzers, file changes confirmed in advance, version
0.1.0 from the local source). The interactive confirmation path was therefore not exercised. The session took
187 s (`duration_ms` 186957 in the stream-json result), 31 turns and $0.09.

The skill found the existing central package management and the existing `tests/Directory.Build.props`, and
produced:

### 6: Stop time

Method: `dotnet-fdg hook turn-start`, then one changed file, then a timed `dotnet-fdg hook turn-stop`, then the file
copied back. The payloads were recorded Claude payloads with `cwd` set to the clone. The change added this method
to `src/Clients/Client.A/Storage/ErrorMapperA.cs`:

```
public static string Probe(int attempt, string key)
{
    try { return key.Trim(); } catch (Exception ex) { return ex.Message; }
}
```

The project has 9 files and references two other `src` projects. The Stop expands the catch, formats the whole
file and reports nothing.

| Case | Runs (s) | Median |
|---|---|---|
| Warm-up | 19.87 | |
| Measured | 20.18, 20.72, 21.18, 21.73, 22.64 | **21.18 s** |
| Codex payload through the real `pwsh -Command "pwsh -File fdg-hook.ps1 turn-stop"` chain | 21.39, 21.31, 21.78 | 21.4 |
| Codex payload, direct | 21.88, 21.81, 21.11 | 21.8 |
| Change that needs no fix (already formatted) | 12.59, 13.19, 12.61 | 12.6 |
| After `dotnet build-server shutdown` (cold, then 2nd run) | 29.06 / 27.01, 30.54 / 26.73 | |
| Warm again | 21.87, 21.36, 21.24 | 21.4 |

Where the time goes. The process trace and separate runs of the same commands from PowerShell agree:

| Step | Time |
|---|---|
| `dotnet-fdg` start to first `dotnet format` | 0.2 s |
| `dotnet format` pass 1, changes the file (workspace load 4.4 s, code style analysis 2.0 s, analyzer pass 0.4 s) | 7.9–8.1 s |
| `dotnet format` pass 2, only confirms that nothing changes (`src/Fdg.Cli/Tooling/FormatPasses.cs`) | 7.6–8.0 s |
| `dotnet build --no-restore` with up-to-date references | 4.2–4.6 s |
| Same build with `--no-incremental --no-dependencies` | 1.3 s |
| git diffs, baseline, SARIF reading | about 0.4 s |

The wrapper and the host make no difference. In this pilot, the same file in the same project took **21.6 s** in
the Claude session, where the AI had run `dotnet build` just before the Stop. It took **31.3 s** in the Codex
session, where the AI had not built and the compiler server had been idle for more than 10 minutes. Timeline from
the state directory: 9.9 s to the end of format pass 1, then 20.2 s to the SARIF log. The cold measurements above
show the same 6–9 s penalty. The earlier Codex figure of about 28 s in [hosts.md](hosts.md) (Codex section) was
measured in a small temporary project; cold build servers are the likely cause there too, but that run was not
repeated.

The common warm case stays below 30 s. A first Stop after a pause comes close to it. The changes that pay off, in
order:

1. **Drop the verification pass.** It costs a full workspace load whenever the first pass changed something. The
   build's SARIF already shows whether nested FDGA003/FDGA023 occurrences are left; rerun format only then. This
   saves about 8 s in every turn with a fix.
2. **Build with `--no-dependencies`** when no file of a referenced project changed this turn. This saves about 3 s.
3. **Resident process (design §5.4)** holding an MSBuildWorkspace and a compiler. This removes the 4.4 s workspace
   load per pass and the cold-start penalty of 6–9 s. `IFormatRunner`/`IBuildRunner` are the seams for it. Worth it
   only if 1 and 2 are not enough.

A measurement trap to avoid in tests and skills: in Git Bash, `dotnet format $PWD/x.csproj --include rel/path.cs`
gets a forward-slash project path and silently formats nothing ("Formatted 0 of 0 files", 5 s). The CLI passes
Windows paths and is not affected.

### 10–14: real sessions

Prompt on both hosts: "add a method that logs a failed upload with 9 details". Both AIs chose
`src/Shared/Lib.Infrastructure/Storage/FailoverUploader.cs`, an existing file of about 520 lines.

**SessionStart.** The context both hosts received, after the manual config fix:

```
This repository follows Framework Design Guidelines (3rd ed.).
- Profiles: src/** = application, tests/** = test. C# 7.3; targets net472. Do not use newer syntax or APIs.
- Write in .NET BCL style: Allman braces, one statement per line, long parameter/argument lists chopped before the first item, one per line.
- Layout and machine-checkable rules are auto-fixed and checked at the end of each turn; only fix the FDG/CA/IDE issues reported to you.
- Before designing or changing types, members, or public APIs, use the fdg-write skill; use fdg-review to review an API.
FDG setup issue: 5 legacy (non-SDK) projects are not supported and are ignored.
```

- Claude: the stream-json `hook_response` of `SessionStart:startup` holds this `additionalContext`, plus the issue
  line as `systemMessage`. The model's first tool call was `Skill framework-design-guidelines:fdg-write`.
- Codex: the model read the fdg-write SKILL.md first. In the resume turn it quoted the context above verbatim.

**Stop auto-fix.**

- **Claude** (115 s by `duration_ms`, 17 turns, $0.04). The AI added `LogUploadFailure` with 9 parameters, one per
  line, and wrote the call as `_logger.Log(level, "Upload attempt failed. ...", scene, filePath, ...)` on two lines.
  The Stop (21.6 s, no output, exit 0) chopped that call to one argument per line, changed `var level` to
  `LogLevel level` (IDE0008), and formatted the rest of the file: 49 ranges, +244 −48 against HEAD. Nothing was left
  to report, so there was no block. On its own initiative the AI also removed a parameter of an existing method and
  two log fields, and asked the user to confirm. That is a model choice, not a plugin effect.
- **Codex** (turn 1: 2 min 38 s wall clock, measured by the calling shell because `codex exec --json` reports no
  duration; 297,387 input tokens of which 206,708 cached, 3,002 output). The AI added `LogUploadFailure` with 9
  details plus the level. The Stop (31.3 s) formatted the whole file (49 ranges) and reported nothing. It left the
  AI's

  ```
  _logger.Log(logLevel,
      "Upload attempt failed. Phase={Phase} ...",
      phase,
  ```

  as written. FDGA023 only checks a list whose opening line is longer than `max_line_length`, so a list broken
  after its first item passes, although the session context asks for "chopped before the first item".
- **Codex hooks**: the actual processes were direct children of `codex.exe`, with `${PLUGIN_ROOT}` substituted:
  `pwsh -NoProfile -Command "pwsh -NoProfile -ExecutionPolicy Bypass -File \"%USERPROFILE%\.codex\plugins\cache\framework-design-guidelines\framework-design-guidelines\0.1.0/hooks/fdg-hook.ps1\" turn-stop"`
  (user profile path shortened). `hooks/list` shows the same substituted command, taken from `commandWindows`. Codex
  loads `hooks.codex.json` through the `hooks` field of `.codex-plugin/plugin.json`. `codex exec resume` runs
  SessionStart again.

**Next-turn summary (Codex).** `codex exec resume <thread> "Quote verbatim (1) ... (2) any FDG note that was added
at the start of this turn. Do not change any files."` (31 s wall clock). The model quoted:

```
FDG auto-formatted at the end of the last turn: src/Shared/Lib.Infrastructure/Storage/FailoverUploader.cs
(lines 40, 42, 51, 53, 64, 66, 73-76, 91-95, ... 507, 509, 521, 523). Re-read those regions before editing them.
```

**Block format and limit.** Neither real session left an unfixable issue, so blocking was checked at hook level. A
turn-start was followed by the planted `ErrorMapperB.cs`, then three Stops with `stop_hook_active` false, true and
true, on both payload forms:

```
{"decision":"block","reason":"FDG found 1 issue(s) in lines you changed this turn. Fix them before finishing.
src/Clients/Client.B/Storage/ErrorMapperB.cs:12 IDE1006 Naming rule violation: These words must begin with upper case characters: describe_failure
    public static string describe_failure(
    FDG3005 DO NOT capitalize any of the characters of any acronyms, whatever their length, at the beginning of a camel-cased identifier.
    FDG3079 DO NOT use a prefix for `public` or `protected` field names.
FDG reformatted files; re-read them before editing: src/Clients/Client.B/Storage/ErrorMapperB.cs      <- Codex only
"}
(stop 2: the same block)
{"systemMessage":"FDG found 1 issue(s) ... Not blocking again this turn (FDG_HOOK_MAX_BLOCKS=2). ..."}
```

The format and the limit of 2 blocks are right, but the quoted rules are wrong. The issue is a method name that
is not PascalCase, so the rule is FDG3001 ("DO use PascalCasing for the names of namespaces, types, members, ..."),
not FDG3005 or FDG3079. IDE1006 maps to 13 rules (FDG3001, 3002, 3005, 3030, 3077, 3079, 3080, FDGA052–057), and
`RulesFor` in `src/Fdg.Cli/Hooks/StopReport.cs` ranks them by word overlap with the message. "characters" and
"case" pull in FDG3005, and "public" pulls in FDG3079.

## Problems found

No Critical problems: nothing broke a build, lost code or touched files outside the onboarded projects.

| # | Severity | Problem | Phase-2 recommendation |
|---|---|---|---|
| 1 | Important | **SessionStart reports false "never built" issues.** A comment that mentions the package id in an ancestor `Directory.Build.props` makes every project below it count as onboarded (`MentionsPackage`, a text search). The first thing the user sees after setup is a wrong instruction. | Decide "onboarded" from parsed `PackageReference` items (comments ignored), or from `obj/fdg/marker.json` plus the restore assets file. |
| 2 | Important | **Wrong rule text for IDE1006** in Stop reports and, presumably, in `/fdg-fix` summaries (not checked). The AI is told to follow an unrelated rule. | Map IDE1006 to FDG rules by symbol kind (type, member, parameter, field, local, const) instead of word overlap; long term, give each naming rule its own diagnostic and carry the symbol kinds in the rule YAML. |
| 3 | Important | **`/fdg-setup` built two projects instead of the solution** and did not check every marker. The cheap model followed step 4 loosely; a project outside every solution stays "never built". | Spell out step 4: build every solution that contains an onboarded project, plus onboarded projects in no solution, then list each onboarded project without a marker. Also tell the skill to keep the package id out of comments, until problem 1 is fixed. |
| 4 | Important | **Hooks run in every git repository.** With the plugin installed at user scope, each turn writes `.git/fdg/<session>/snapshot.json` in any git repository, and Stop takes about 0.9 s even where no project is onboarded (temporary repository test). State directories are never cleaned up. | Gate turn-start and Stop on the onboarding check, so that the plugin costs nothing elsewhere; delete state directories of old sessions. |
| 5 | Minor | **FDGA023 does not enforce "chopped before the first item"** for lists broken by hand when the opening line is short. The session context promises that style. Seen in the Codex session. | Decide whether FDGA023 also reports multi-line lists that are not chopped, whatever the line length; if not, change the context text to "lists longer than the line limit". |
| 6 | Minor | **Stop time**: 21 s warm, 27–31 s with cold build servers. The verification-only second format pass takes about 8 s of the 21 s (about 37%). | Skip the verification pass when the build's SARIF shows no remaining FDGA003/FDGA023 in the changed files; build with `--no-dependencies` when no referenced project changed; consider the resident process (design §5.4) only afterwards. |
| 7 | Minor | **A permanent condition reported as a setup issue every session**: "5 legacy (non-SDK) projects are not supported and are ignored." is shown to the user and added to the AI context in every session, although nothing can or should be done about it. | Report legacy projects once, in `/fdg-setup`; at most keep them in the AI context, not in `systemMessage`. |
| 8 | Minor | **The auto-fix record of a turn is overwritten by later Stops.** In the hook-level test, Stop 1 reformatted and Stops 2–3 found nothing to reformat, so the next turn-start had no summary. The block reason of Stop 1 did carry "re-read" on Codex, so the AI was told once. | Merge the auto-fix records of all Stops in the turn. |
| 9 | Minor | **The next-turn summary of a whole-file reformat** lists 49 ranges. It costs tokens and says little more than "the file was reformatted". | Above a threshold (for example 10 ranges, or more than half the file), say "reformatted throughout". |
| 10 | Minor | **A first `fix` of existing code is large**: 184 of 453 files in `src`. IDE0008 alone has 2333 hits. Stop is not affected (it reports changed lines only). | Keep IDE0008 at warning; tell `/fdg-fix` users to expect a large first diff and to commit it separately. |

host, the interactive confirmation path of `/fdg-setup`, and re-approval of Codex hooks after a plugin update.
