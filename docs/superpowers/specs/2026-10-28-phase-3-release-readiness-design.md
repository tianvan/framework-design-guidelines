# 第三期设计：发布准备，迈向 1.0

日期：2026-10-28。上位文档：`docs/superpowers/specs/2026-10-21-framework-design-guidelines-design.md`（以下简称“总设计”）和 `docs/superpowers/specs/2026-10-23-phase-2-chapter-expansion-design.md`（以下简称“第二期设计”）。本文只写第三期新增或细化的决定；前两份文档中的约定继续有效，这里不再重复。

范围来源：用户要求“直接根据 docs/phase-2-backlog.md 定范围”（2026-10-28），并跳过了逐项提问。所以本文中凡是没有标“用户决定”的取舍都是我的决定，用户审阅时可以推翻。另外两个来源：总设计 §7 第 3 步（发布准备）和 §8（实现阶段必须验证的事项）中还没有验证的条目。

## 1. 意图

规则已经覆盖全书：830 条，全部 `verified`。0.2.0 已经发布到 nuget.org 和 GitHub。插件目前还没有人在日常工作中使用（用户，2026-10-28）。

第三期要把它做成一个可以放心推荐给别人、自己也愿意每天开着的 1.0。具体是四件事：
- AI 收到的信息必须准确，不能漏报，也不能把已有 API 当新代码打回；
- 每轮结束时的等待要短；
- 在两个宿主的真实会话里确认链路可用，包括目前只在 hook 层面测过的路径；
- 文档写清楚能做什么、不能做什么、版本怎么演进。

第三期以发布 1.0.0 结束。

## 2. 目标、非目标、反目标

### 目标

1. `docs/phase-2-backlog.md` 中的每一项都有结论：做完并有测试，或者移入发布后的待办（`docs/backlog.md`）并写明理由。
2. 总设计 §8 中尚未验证的事项都完成验证，结果记录在文档中；做不到的写明“未验证”。
3. Stop 的常见情况（单文件、热启动）明显变快，前后数据在同一台机器、同一个仓库上测得。
4. 发布工程可靠：最低 SDK 有 CI 实测；Actions 固定到提交 SHA；有版本兼容承诺和变更记录。
5. 先发布 1.0.0-rc.1，在真实宿主上验证后再发布 1.0.0。

### 非目标

- 不新增规则，也不新增章节（全书已经覆盖完）。
- 不新增自写分析器。例外：为修复 backlog 中已有问题而对现有分析器做的改动。
- 不做常驻进程（总设计 §5.4）。只有在本期的优化完成后，常见情况仍然明显超过 30 秒，才把它作为一个决定交给用户。
- 不做 IDE 扩展，也不支持更多宿主。
- 不加 Dependabot 等会自动开 PR 的机器人（我的决定：它们会在用户的仓库里自行产生外部动作）。

### 反目标（任何一条出现，即使功能“能用”也算失败）

- 自动修改已发布的 API，或者替用户提交（总设计 §2）。
- 已安装 0.2.0 的用户升级后，hook 静默失效（例如协议不兼容但没有提示）。
- 为了提速而漏掉本该报告的问题，例如跳过验证轮次后格式问题没有被修复，却也没有报告。
- 第三期中多次修改 `hooks.codex.json`，让 Codex 用户反复重新批准 hook。
- 写进仓库的任何内容泄露试点或内部仓库的信息。

## 3. 约束

沿用前两期的约束，这里只列出与第三期相关的：

- `private-sources/` 中的 epub 不可信：只读，读取它的脚本用 `python -I` 运行，不执行其中的任何内容；`private-sources/` 永不提交。第三期只在规则 notes 有改动、需要做 8 词复制检查时才读它（`check --book`）。
- 试点克隆：不做 git 操作，不修改；只能通过 `eng/noise/Measure-Noise.ps1` 使用。用户的内部仓库不得修改。写进仓库的结果一律匿名（只用 internal-a、internal-b 和计数）。
- 不复制任何凭据或认证文件。不改用户的 Claude 和 Codex 配置，已批准的条目除外。
- 每次 push、开 PR、合并、打 tag、发布之前，都先征得用户同意。0.2.0 的授权不延续到第三期。
- `hooks.codex.json` 在第三期最多改一次（见 §4.4）。
- 规则数据仍是唯一来源；生成的文件只由 `generate` 写出。

## 4. 范围与决定

按工作流分组。每一项对应 backlog 中的条目，没有新增 backlog 以外的工作；例外都已注明来源。

### 4.1 发布工程

1. **最低 SDK 改为 10.0.100**（第二期设计 §8a 已定，本期落实；具体做法是我的决定）：
   - `SelfCheck.MinimumSdkVersion` 与 `FullCoverageSdkVersion` 合并为一个值 10.0.100。低于它时，SessionStart 报告一条 setup issue，说明 SDK 低于支持的最低版本、部分规则不会运行。这条提示不指向 `/fdg-setup`，因为用户未必能升级 SDK。hook 照常运行，与现在一样，不新增阻断。
   - 理由：文档声称支持却从不测试的版本是陷阱。.NET 10 是 LTS，SDK 版本又与目标框架无关，项目仍然可以面向 net472 和 C# 7.3。插件目前也还没有用户。
   - CI 增加一个 job，在 SDK 10.0.100 上运行集成测试。需要更新 SDK 的测试，要么标出原因后跳过，要么改成与版本无关。
   - 同步修改 README、`docs/install.md` 和 SessionStart 的提示文本。
2. **Actions 固定到提交 SHA**：
   - 改为能在 Node.js 24 上运行的版本，行尾注释写明版本号；
   - CI 日志中不再出现 Node.js 20 弃用警告；
   - `release.yml` 中的 `NuGet/login` 同样处理。
3. **参考文件名统一为小写**，例如 `appA-coding-style.md` 改为 `appa-coding-style.md`：
   - 理由：Linux 上路径区分大小写；拆分出来的文件名已经是小写；1.0 之后路径会被引用，不宜再改；
   - skill 中的路由表、测试和文档链接随之更新。
4. **版本与兼容承诺**（我的决定），写进 `docs/releasing.md` 的新一节：
   - FDG 和 FDGA 编号永不复用，也不重新编号。
   - 主版本号：删除诊断编号，删除或改名 CLI 命令和选项，hook 或 `rules.json` 协议发生不兼容变化，提高最低 SDK。
   - 次版本号：新增诊断，提高严重级别，改变 profile 的默认值。这些可能让 `TreatWarningsAsErrors` 的构建失败，所以每次都在变更记录中单独列出。
   - 修订号：只减少误报、修复崩溃或修正文案。
   - 插件与工具的版本匹配规则按现有协议检查写明，第三期不改变协议的含义。
5. **变更记录**：新增 `CHANGELOG.md`，从 1.0.0 开始，用一段话概括 0.1.0 到 1.0.0 的变化。GitHub release 继续使用 `--generate-notes`。
6. **README 的发布前收尾**（总设计 §7 第 3 步）：
   - 去掉 “Preview” 段落；
   - 加一个简短的前后对比：一段 AI 写的 C# 代码在 Stop 自动修复和报告前后的样子，以及 fdg-review 的一条输出。示例代码自己写，不取自书中；
   - 核对安装、覆盖率、声明和 NOTICE。

### 4.2 让 AI 收到的信息更准确

1. **ExistingApi 比较基类列表**：
   - 位置在类型声明上的诊断（例如 CA1063 报告在类型名上），除了比较声明是否已经存在，还要比较基类和接口列表与本轮开始时是否相同；
   - 本轮新加了 `IDisposable` 的类型，它的 CA1063 属于本轮的改动，应当打回；
   - 测试覆盖 backlog 中描述的场景，以及基类列表没有变化的对照情况。
2. **可见的 const 同时属于两种种类**（Ruling 54）：
   - `DeclarationLocator.FieldKind` 把可见的 const 同时归为 `constField` 和公开字段的种类；
   - 写错大小写的 `public const` 能引用 FDG3077 和 FDG3001，私有 const 仍然只引用 FDGA053。
3. **CA1710 的 `exclude_indirect_base_types`**（Ruling 48）：
   - 先在噪音样本上运行 `false`，覆盖 FDG3048–3059、FDG3076、FDG7057、FDG8005、FDG8038 和 FDG8039；
   - 误报不超过第二期设计 §5 的门槛（1/20）时，在 globalconfig 中把它设为 `false`，FDG3049、3053、3056、3059、3076 的覆盖改回 `full`，notes 同步修改；
   - 超过门槛时保持现状，在 notes 和 `docs/noise-samples.md` 中写明数据。
4. **IDE0280、IDE0250、IDE0251 需要 `.editorconfig`**：
   - `/fdg-setup` 在它确认的改动清单中，提议在根 `.editorconfig` 的 `[*.cs]` 节写入这三条诊断的严重级别（取当前 profile 的值），用户确认后才写入；
   - 实现者先用 probe 确认没有更简单的途径（例如包内的其他配置方式）；如果有，改用那条途径，并在计划中说明；
   - FDGA048 的 notes 和 `docs/install.md` 随之修改。
5. **参考文件也列出部分检查的规则**（Ruling 22，我的决定：列出）：
   - 现在 `SkillReferenceEmitter.IsListed` 只收录判断类规则和 sdk/fdg 的 CONSIDER 规则，223 条 `partial` 的 DO、DO NOT 和 AVOID 规则 AI 看不到，而它们恰好有一部分是工具查不到的；
   - 这些规则加入参考文件，带标记 “(partly checked)”。fdg-write、fdg-review 和 fdg-reviewer 说明这个标记：工具只检查规则的一部分，其余部分由 AI 自己遵守或评审；
   - 估算约增加 25–30 KB 原文，分摊到 22 个参考文件，每个文件仍远低于 32 KB 的上限。如果实际超出上限，按现有的拆分配置继续拆分；
   - `full` 的 sdk/fdg 规则仍然不列出。
6. **globalconfig 键冲突**：两条规则写同一个 globalconfig 键、但严重级别不同时，`check` 报错并列出这两条规则，而不是静默取第一条。当前数据没有这种情况，用测试覆盖。
7. **一轮内的自动修复记录**（试点问题 8、9）：
   - 同一轮的多次 Stop 合并自动修复记录，后一次不再覆盖前一次；
   - 范围数超过阈值（例如 10 个），或者覆盖了文件的一半以上时，下一轮开头的摘要写 “reformatted throughout”，不再逐个列出范围。

### 4.3 Stop 耗时

试点测得：单文件热启动中位数 21.2 秒，冷启动 27–31 秒；第二轮只做验证的 `dotnet format` 约占 8 秒。

1. **先测基线**：
   - 在做任何 hook 改动之前，用 0.2.0 测一次基线：热启动 5 次取中位数，另测冷启动；
   - 测量用一个开源噪音样本的临时副本，在副本里放入一处单文件改动。不用试点克隆，因为它不能修改；
   - 测量脚本放在 `eng/perf/`，可以重复运行。
2. **优化**：
   - 只有当构建的 SARIF 显示改动文件中仍有 FDGA003 或 FDGA023 时，才运行第二轮验证；
   - 本轮没有改动被引用的项目时，用 `--no-dependencies` 构建；
   - 测量多项目的轮次（2 到 3 个项目）。如果串行构建明显拖慢，改为一次 MSBuild 调用构建多个项目，具体做法由实现者决定。
3. **目标**（我的决定）：
   - 热启动单文件的中位数比 0.2.0 基线至少低 30%，冷启动低于 30 秒；
   - 达不到时，在文档中写明原因和数据，并把常驻进程作为待用户决定的事项提出，不在本期实现；
   - 任何提速都不能让本该报告的问题消失（反目标）。测试覆盖“跳过验证轮次但仍有 FDGA003 或 FDGA023”的情况。
4. **全部规则开启后的构建开销**（总设计 §8）：
   - 给 `Measure-Noise.ps1` 加一个计时模式，在 5 个样本上比较加包前后的构建时间；
   - 结果写进新的 `docs/performance.md`，与 Stop 的数据放在一起。内部样本只写匿名的计数和时间。

### 4.4 hook 与 CLI 的健壮性

1. **包装脚本**（我的决定：与 Codex 的引号修复一起，作为本期唯一一次 `hooks.codex.json` 变更）：
   - 去掉每次 hook 都要运行的 `dotnet-fdg --version` 探测：版本和协议检查交给 hook 入口自己完成，每个 hook 只启动一个进程；版本不匹配时仍然给出清楚的提示（反目标：静默失效）；
   - 备用的工具位置考虑 `DOTNET_CLI_HOME`；sh 包装脚本在 Windows 上使用 `USERPROFILE`；
   - 非 UTF-8 的 stderr 转成 UTF-8，或者安全地替换无法解码的字节；
   - 仓库本地工具清单中固定了 `dotnet-fdg` 版本时，hook 使用这个版本。
2. **Codex 在 Windows 上的 `${PLUGIN_ROOT}` 引号**：
   - 路径不再放在会展开 `$` 和反引号的 PowerShell 双引号字符串中；
   - 测试中使用一个含空格、CJK 字符、`$` 和反引号的插件路径；
   - `docs/install.md` 和 README 写明：从 0.2.0 升级到 1.0 需要重新批准一次 hook。
3. **接入判断**：
   - `obj/project.assets.json` 现在只用来否决；
   - 改为：assets 文件列出了这个包时，即使包引用来自检查没有跟踪的 import，也算已接入。
4. **边界情况**，每项都配测试：
   - 路径中含 `;` 或 `,` 时，`-p:FdgSarifDir`、`-p:FdgSarifProject` 和 `ErrorLog` 要转义，或者改用不受影响的传参方式；
   - `ProjectInfoProvider` 像 `SessionContext` 一样，先确认 marker 属于这个项目再读取；
   - 切换到 `UseArtifactsOutput` 之后，`obj/fdg` 中过期的 marker 不能压过 `artifacts/` 中较新的 marker：两处都查，取较新的那个；
   - 符号形式的 LangVersion（latest、preview、default）显示为实际生效的版本，取不到时写明原样；
   - 所有结果都在链接的 `Compile` 项中时，`IsForeign` 不强制重建；
   - `formatted/` 副本和 `ai-lines.json` 原子写入（先写临时文件再改名）；
   - SessionStart 的 Inspect 可以取消，并受超时约束；
   - 在不是 git 仓库的目录中，`FindOwningProjects` 不再一路走到盘符根目录，而是在用户主目录或仓库边界处停下，具体边界由实现者决定；
   - `fix` 对无法编译的文件不显示 “fixed”，而是说明原因；
   - Windows 上单个文件的 `--include` 列表过长时，改用响应文件或分批执行。
5. **文档**：
   - `docs/install.md` 增加一句：hook 会在仓库中运行 `dotnet build` 和 `dotnet format`，所以只在可信的仓库中使用；
   - backlog 中列出的已知限制，`docs/install.md` 已经写明。本期只按上面的改动更新相应条目，例如自定义输出路径中 `UseArtifactsOutput` 的部分。

### 4.5 生成器

1. `check` 不再依赖 `DotnetTools/dotnet-format` 的 SDK 内部布局，或者在布局变化时给出明确的错误，指出期望的路径；SDK 从当前目录解析，与 `global.json` 的结果一致，不再从 `--rules` 的父目录解析。
2. YAML 错误给出文件名、行号和列号（`YamlException.Start`）。
3. 只在编译结束时报告的诊断（FDG5077、FDG6019）带上 `WellKnownDiagnosticTags.CompilationEnd`；由生成器根据规则数据或分析器的声明写出 `customTags`，并在分析器项目中把 RS1037 设为 error，避免以后再出现遗漏。

### 4.6 仓库卫生

1. 仓库自己的 `.editorconfig` 中，私有字段的命名规则对 `const` 加例外。
2. FDGA003 和 FDGA023 的 CodeFix：
   - `catch { /* ignore */ }` 中的注释移进块内；
   - 列表项之前的 `/* c */` 留在原来的项前，不随逗号移动；
   - 含两个块的 switch section 一次修完；
   - 计算行长时，制表符按 `.editorconfig` 的 `tab_width` 计算，默认 4。
   - 每种情况都配 CodeFix 测试。改动后在噪音样本上复跑 FDGA003 和 FDGA023，结果不能变差。

### 4.7 真实宿主验证

有 1.0.0-rc.1 之后，用正式的安装路径验证：nuget.org 上的包，加上 GitHub 上的 marketplace。验证用一个专门新建的临时仓库进行，里面有一个小类库和一个测试项目，预先埋好违规；不用试点克隆，也不用内部仓库。这个临时仓库不推送到任何地方，用完后由用户决定是否删除。

| 事项 | 来源 | 谁来做 |
|---|---|---|
| Codex `$fdg-setup` 的调用形式 | backlog | 用户操作，我准备步骤 |
| Codex 长会话压缩后 SessionStart 是否重新注入 | backlog、总设计 §8 | 用户操作 |
| 插件从 0.2.0 更新后 Codex hook 的重新批准 | backlog、总设计 §8 | 用户操作（先装 0.2.0，再更新） |
| `/fdg-setup` 的交互确认路径 | backlog | 用户操作 |
| 两个宿主在真实会话中被 Stop 阻止时的行为和次数上限 | 总设计 §8、试点未测 | 能用无界面模式（`claude -p`、`codex exec`）的部分由我来做，其余由用户操作 |
| Visual Studio 和 VS Code（C# Dev Kit）实时分析是否识别包内的 globalconfig | 总设计 §8 | 用户打开临时解决方案查看错误列表 |
| Rider | 总设计 §8 | 本机没有安装：文档写“未验证” |

- 我先写好一份逐步清单，交互部分合并成用户的一次操作，预计约 30 分钟。
- 结果写进 `docs/hosts.md`：日期、宿主版本、通过或失败，以及观察到的行为。
- 发现的问题在 rc 之后修复：先开一个小分支修，如果改动影响发布的内容，就发 rc.2。

## 5. 工作顺序与流程

沿用第二期的流程：实现者按任务说明工作；规范和代码评审并行；改动了规则 notes 的任务，额外对照 epub 复核；修复轮次交给原来的 agent；最后由我更新台账。另开 `phase-3` 分支。

1. **测基线**（§4.3 第 1 步），必须在任何 hook 改动之前完成。
2. **低风险的机械改动**：§4.1 第 1–3 项、§4.5、§4.6。
3. **信息准确性**：§4.2。CA1710 先跑噪音样本再做决定。
4. **hook 与 CLI**：§4.4。所有涉及 `hooks.codex.json` 的改动放在同一个任务中。之后做 §4.3 第 2–4 步。
5. **文档**：§4.1 第 4–6 项、§4.4 第 5 项、§4.8。
6. **全分支终审**：修复后开 PR，由用户决定是否合并。
