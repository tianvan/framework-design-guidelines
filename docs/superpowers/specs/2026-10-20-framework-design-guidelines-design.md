# framework-design-guidelines 设计草案

状态：待审阅。项目名与初始化已批准；以下结构、预算和执行方式属于建议设计，不表示插件实现已获批准。

## 1. 目标与已确认要求

将 *Framework Design Guidelines: Conventions, Idioms, and Patterns for Reusable .NET Libraries (Addison-Wesley Microsoft Technology Series)* 第三版（2020）全书提炼为可维护、可定位来源、按需加载的规范体系，作为 Codex 与 Claude Code 插件分发。

范围限定为可复用 .NET 库及组件。公共 API 的命名、类型与成员、扩展性、异常、异步、资源管理及兼容性是核心；附录 A 的 C# 排版、命名、注释和文件组织也纳入覆盖。对应用内部代码的适用范围需要显式声明。

两端共用规则来源和验证资产，避免维护两份规范。控制 token 消耗，并以真实任务评测判断加载与执行效果。

## 2. 原书来源与覆盖

需要可核对的第三版正文。原书本机路径尚待用户提供。原始正文保存在使用者指定位置或被忽略的 `private-sources/`，不进入 Git 提交及插件发布包。

规则来源保留版本、章节、页码和校验信息。规则使用独立摘要表述；重要例外不能因缩写而删除。未核对条目保留未核对状态，不伪造原书定位。

覆盖目录逐章登记：提炼为规则、保留为设计背景、历史废弃指导、项目不适用或待核对。全书覆盖不意味着将所有叙述都转成硬性要求。

在线第二版摘要、现代官方仓库实践及团队偏好单独标识；不得混入第三版规则而不注明来源。

## 3. 核心规则模型

建议每条规则包含：稳定编号、独立摘要、原始强度、适用范围、触发条件、理由、例外、第三版来源、相关规则、检查方式、核对状态。

编号由项目建立，不冒充原书自带编号。一个原书条目拆分或跨主题引用时，保留可追踪关系。

使用项目的语言版本、运行时、公开契约及例外放在独立配置中。项目覆盖不能悄悄改写原书条目。目标仓库已有公开契约变化需要兼容性审查，不能为符合一条规则而自动破坏 API。

## 4. 上下文加载

常驻入口只描述范围、规范版本、主题选择、兼容性和检查入口。按当前改动主题读取相关规则，公共 API 改动额外加载 API 设计与兼容性要求。

建议初始入口预算不超过约 500 token；单个主题摘要约 800 至 1,500 token。具体预算通过双端评测确定，不作为尚未测量的效果声明。

需要评测普通读取、编辑、多文件 shell 命令、CodeGraph / MCP 读取、子代理和上下文压缩后的行为。仅匹配 `.cs` 后缀不能决定完整设计规则的适用范围，仍需判断变化是否涉及公共 API、异步、资源管理等主题。

## 5. 双端插件边界

建议组件：

```text
plugin.json                    可移植插件清单
.codex-plugin/plugin.json      Codex 兼容适配（需要时）
.claude-plugin/plugin.json     Claude Code 插件清单
skills/                        共用任务入口及按需参考资料
standards/                     规则目录、来源、检查映射、目标项目配置
adapters/                      宿主差异与生成辅助
scripts/                       范围选择和统一检查入口
evals/                         双端加载及行为评测
docs/                          设计、来源及维护说明
```

最终目录和清单字段须由当前官方文档及本机宿主验证确认。平台清单引用同一份 `skills/`，不复制规则正文。采用生成方式时，检查生成结果与源数据没有漂移。

第一阶段建立清单与 Skills 的加载验证。文件访问时自动注入规则属于第二阶段候选：两端 Hook 检查工具参数并返回少量规则或加载指引，避免逐次重复注入。Hook 信任、不同工具覆盖和压缩后恢复必须分别验证。

安装、配置写入和发布操作采用明确、可审阅的入口；安装插件不等于修改使用项目的编码规范或启用所有检查。

## 6. 自动检查与设计审查

机械排版由一个主 Formatter 负责；命名和可静态分析的设计规则使用精选 Analyzer；兼容性使用 API 基线与对应测试。默认工具与版本在规则映射后确定，不预先声称某个工具完整覆盖第三版。

规则映射至少标记：自动修复、自动检测、部分检测、设计审查、历史背景、不适用。Formatter 和 Analyzer 只在覆盖范围内提供保障。

API 易用性、合理抽象、扩展性取舍、异常契约和行为兼容通过调用方示例、针对性测试和设计审查判断。提示词不得用“全部通过”掩盖尚无检查器的条目。

## 7. 评测与验收

分开记录：来源核对及章节覆盖、宿主清单验证、规则加载、首次生成遵循、修正后遵循、最终交付、误报与例外识别、token 及修正次数。

建议首批使用 20 至 30 个代表性任务，对照无规范、按需规范、按需规范加工具检查三种设置。两个宿主使用同一任务及规则版本，记录实际模型、推理设置、CLI 版本、源代码和检查输出。

包含违规样例、正确样例和允许例外；用独立评分与必要的人工核对避免仅凭生成者自评。初次样本用于发现问题，不外推整书遵循率。

插件加载成功、模型读过规则、构建成功和最终遵循是不同结论。对自动检查范围以外的要求保留明确的审查结果。

## 8. 分阶段工作

1. 当前：初始化仓库，确认原书来源，审阅设计。
2. 编写实施计划：规则模型、加载接口、清单、工具检查及评测任务。
3. 用少量核对主题完成双端加载与检查试点，依据数据调整设计。
4. 逐章扩展到全书，保留解释、例外、历史条目及覆盖证据。
5. 固定规则与工具版本，完成分发验证和真实任务评测后再发布。
