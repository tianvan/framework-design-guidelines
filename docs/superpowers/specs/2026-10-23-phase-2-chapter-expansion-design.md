# 第二期设计：逐章扩展到全书

日期：2026-10-23。上位文档：`docs/superpowers/specs/2026-10-21-framework-design-guidelines-design.md`（以下简称“总设计”）。本文只写第二期新增或细化的决定；总设计中已有的约定（规则格式、生成器、profile、分析器配置、skill 结构、反目标等）继续有效，这里不再重复。

## 1. 意图

用户的要求（原话）：“遵守这本书的准则来写代码。”第一期只覆盖了第 3 章命名和附录 A 排版。第二期要让 AI 在 C# 代码中遵循全书的准则，包括类型设计、成员设计、可扩展性、异常、使用准则和常用设计模式。这些章节决定了 API 是否好用、代码是否可读。

做法沿用总设计：
- 能机器检查的准则交给分析器，并尽量自动修复；
- 需要判断的准则以原书原文提供给 AI，写代码前由 fdg-write 按需读取，评审时由 fdg-review 逐条对照。

## 3. 前置工作：扩展章节前必须修好的抽取问题

第 4 章以后的书页大量使用列表、表格、行内代码和跨多段的示例。下面这些问题如果不先修，原文会被抽错，而且 verify-source 发现不了，因为它只是重复同一个错误：

1. **抽取器保真**：
   - sidebar 中的 `ul`、`ol` 和 `table`，以及行内的强调、代码、链接、`<br>`，要按 Markdown 保留，不能压平；
   - 需要在第一期两章上回归：第 3 章和附录 A 重新抽取后，原文字段变化必须为零，或者每处变化都是修正了原先的压平；
   - 对第 4–9 章各抽一次骨架，检查列表和表格是否完整（只做检查，不提交骨架）。
2. **过期参考文件**：
   - `generate` 要删除不再由规则数据产生的 `references/` 文件；
   - drift 检查要能发现多出来的旧文件。
3. **连字（ligature）残留**，例如 3.4.1 的 “Conf licts”：
   - 我的决定：在 Normalizer 中修复 epub 文本里被拆开的 fi/fl/ff 连字，每种模式都配一个测试；
   - 修复后用全书重新抽取的结果比较差异，只允许出现连字修复带来的变化；
   - 原则仍然是“不改写原文”，修复连字属于还原原文。
4. **维护者工具的错误信息**：verify-source、extract、check 遇到格式错误的 YAML、找不到 dotnet、Schema 加载失败时，输出一行说明，不打印栈追踪。全书扩展期间要反复运行这些工具，所以放在前面做。
5. **IDE1006 按符号种类对应规则**（backlog “Rule mapping” 第 1 项）：
   - 命名规则的 YAML 增加符号种类标签；
   - CLI 根据诊断位置的符号种类和失败类型，选出对应的规则原文。
   - 第一期的最小修复（宁缺毋错）已经上线。这一项让命名问题能引用正确的规则，是“遵守这本书”最常见的反馈路径，所以放进第二期。
6. **FDGA023 的范围**（backlog “Rule mapping” 第 2 项）：
   - 按附录 A 原文判断“手工断行但不是在第一项之前断行”的多行列表是否算违规；
   - 原文支持就扩大 FDGA023 的范围，否则把会话上下文的措辞改为与分析器一致；
   - 由交叉核对代理判定，判定写进该规则的 notes。

## 4. 逐章流程

每章一轮，严格按总设计 §5.8：
1. 抽取；
2. AI 映射，状态为 `draft`；
3. 自动校验：条目数等于图标数，通过 Schema，原文与重新抽取的结果一致，映射的规则编号存在；
4. 独立代理交叉核对，通过后改为 `verified`；
5. 登记非准则内容。

第二期补充的决定：

- **顺序**（我的决定）：先做前置工作，再按书的章节顺序推进：2、4、5、6、7、8、9、附录 D。
  - 后面的章节经常引用前面的规则，例如第 5 章引用第 4 章的类型选择，第 9 章引用第 5、7 章。按顺序做，交叉核对时被引用的规则已经是 `verified`。
  - 第一版发布前必须全书完成，所以先做哪章不影响发布时间。
- **大章拆分**：第 5 章（133 条）和第 9 章（175 条）按书的一级小节拆成两到三轮。每轮仍是完整的五步，只是范围缩小，便于交叉核对逐条读原书。
- **规则编号**：沿用总设计 §6 的格式（`FDG` + 章号 + 序号；附录用字母，如附录 D 为 `FDGD`），与第一期一致。
- **映射时逐条决定**：
  - 对应的 SDK 规则（CA/IDE）：以 `sdk-catalog` 列出的、当前 SDK 实际存在的诊断为准；
  - 能否机器检查、能否自动修复，以及修复是否会破坏 API（`autofix: breaking` 的诊断永远不进自动修复）；
  - 适用的 profile；
  - 依赖的语言版本，带替代写法。
- **profile 的默认值**（我的决定，可在 YAML 中逐条覆盖）：
  - `library` 和 `application`：全部启用。application 档覆盖应用内部的层间契约和实现，与总设计 §5.1 一致。
  - 只对公开 API 有意义的规则（如附录 D 的破坏性变更、多数版本兼容和可扩展性规则）：只用于 `library`。
  - `test`：启用第 7 章（异常）、第 8 章（使用准则）和附录 A；不启用第 2、4、5、6、9 章和附录 D 的设计类规则。测试项目一般不对外公开 API。个别规则如有例外，在映射时逐条决定。
- **交叉核对**：每章由一个独立代理对照原书逐条核对，检查映射、profile、例外条件，以及示例代码是否完整（尤其是跨多个代码块或带批注的条目）。用户只做抽查：每章给用户一份 10 条左右的抽查清单，汇总到第二期结束时一起交付，不阻塞推进。

## 5. 自写分析器

总设计 §5.2 的标准不变：判定精确、确定性强、误报率低；以符号级分析为主；对公开 API 改名永远不自动修复。第二期补充：

- **候选来自映射**：映射时，对“能机器检查、但 SDK 没有对应规则”的条目标记为自写分析器候选，写明检查方法。候选是否实现，按下面的门槛决定，不设固定数量。
- **实现门槛**（我的决定）：
  1. 能用语法树或符号信息直接判定，不需要猜测意图；
  2. 在噪音样本上的误报率低：在开源 .NET 代码和试点克隆上运行，抽查报告结果，误报不超过 1/20（样本和“误报”的定义见第 7 节）；
  3. 有 CodeFix 时，修复必须不改变公开 API 的签名或名称，并支持 FixAll。
  - 不满足门槛的候选保留为判断类规则，在 notes 中写明原因，以后可以重新评估。
- 第一期识别出的第 3 章低成本检查（总设计 §5.2 列出的那些）在第二期一并评估和实现，因为它们直接影响“命名是否遵守本书”。
- 每个自写分析器都要有：正例和反例测试、针对最低支持语言版本（C# 7.3）的测试、CodeFix 测试（如果有），以及规则文档页（helpLink）。
- 分析器的诊断编号即规则编号（总设计 §5.2）。

## 6. 让 AI 看到并遵循：skill 与参考文件

规则数量从 158 条增加到 830 条，但 AI 每次写代码时读到的内容不能随之线性增长（总设计 §2 的 token 目标）。决定（我的）：

- **fdg-write 的 SKILL.md**：
  - 继续手写，保持在 500 行以内；
  - 放全书中最重要的几十条判断类规则（原文、编号），按重要性排序，最关键的放在最前面；
  - 加一张路由表，写明“设计类型时读哪个文件、设计成员、属性、事件、异常、集合、Dispose 或 async 模式时各读哪个文件”。
- **参考文件按主题拆分**：
  - 每章一个或多个文件，大章按小节分组；
  - 每个文件都应该能在一次读取中完整读完：上限约 8k token，约 32 KB 的英文 Markdown；
  - 只收录判断类规则和只被分析器“建议”的 CONSIDER 规则（与总设计 §5.5 一致）；
  - 示例代码和长解释放进二级 examples 文件；
  - 由生成器产生，规则数据是唯一来源。生成器需要支持“一章多个参考文件”的拆分配置（写在 `meta.yaml` 中）。
- **fdg-review**：
  - 按被评审代码涉及的主题读对应的参考文件；
  - 评审库的公开 API 时，附录 C 的规范示例作为背景；
  - 报告继续按规则编号引用原文。
- **会话注入**：保持简短，不随规则数量增长。只在设计规则覆盖范围扩大后补一句提示：设计或修改类型、成员、异常处理和常见模式前先用 fdg-write。
- **验证**：每章完成后，用 skill lint 测试检查 SKILL.md 和参考文件引用的规则原文与规则数据逐字一致（第一期已有的测试扩展到新文件），并检查每个参考文件的大小上限。

## 7. 噪音样本

新开启的 CA 规则和新的自写分析器，都可能在已有代码上产生大量警告（反目标“误报多、刷屏”）。Stop 只报告本轮改动的行，但 IDE 和构建会显示全部警告。决定（我的）：

- 样本使用公开的开源 .NET 代码。在临时目录中浅克隆 2 到 3 个知名的、SDK 风格的开源库，构建并统计每个新诊断的数量，抽查误报。
  - 选库标准：活跃维护，代码风格接近 BCL，规模中等（构建在几分钟内完成）。
  - 选定的仓库和提交写进第二期的计划。
- 每章完成时记录：新增的诊断各报告了多少条，抽查了多少条，有几条误报。
  - 误报超过门槛的 SDK 规则：降级为 `suggestion`，或者在 notes 中写明例外条件并收窄映射；
  - 误报超过门槛的自写分析器：不发布。
- 样本另外包括试点克隆（用户决定，2026-10-23）。
  - 只构建、统计和抽查，不做任何 git 操作，也不修改源文件。需要的包引用和 profile 配置只留在克隆的工作树中，测完后用普通复制还原。
  - 写进文档的结果全部匿名，不出现项目、命名空间或路径的名称。
- “误报”的定义：报告的位置实际符合书中准则的原文，包括原文写明的例外。判定标准是逐条对照原文，与代码整体是否规范无关。代码不规范产生的真实警告不算误报，但要单独记录它们的数量，用来判断是否会刷屏。

## 8. 完成标准

第二期完成时必须满足：

1. 第 2、4–9 章和附录 D 的 672 条规则全部是 `verified`。第一期的 158 条在抽取器修复后重新校验，仍为 `verified`。
2. 覆盖率文档覆盖全书每一章和每个附录（含附录 B、C 和前言），逐节写明非准则内容的去向。
3. 生成器的 drift 检查干净，没有多出来的旧文件。`check` 通过：映射的诊断都存在于固定的 SDK 中。
4. 通过门槛的自写分析器全部实现并有测试。未通过的候选都在规则 notes 中写明原因。
5. fdg-write、fdg-review 的引用和大小测试通过，每个参考文件都在大小上限以内。
6. 噪音样本的记录写进 `docs/`，内容包括每章新增诊断的数量、抽查数和误报数。
7. 全部测试通过，CI 在 Windows 和 Ubuntu 上都是绿的。
8. 用户抽查清单汇总交付，每章约 10 条。

## 8a. 设计审阅后补充的决定（我的决定）

- **SDK 基准**：
  - 映射以固定的 SDK 10.0.402 的诊断目录为准，不为每条诊断记录它在哪个 SDK 版本中引入。
  - 完整的规则覆盖以 SDK 10.0.100 为最低要求。更老的 SDK 不带某条诊断时，这条规则在构建中不出现，这是已知后果。
  - SessionStart 的自检在 SDK 低于 10.0.100 时加一行说明（“some rules need SDK 10.0.100 or later”），避免静默失效。
  - 目标项目仍然可以面向 net472/netstandard2.0、C# 7.3，因为 SDK 版本与目标框架无关。第三期发布时，文档写明的最低 SDK 随之改为 10.0.100。
- **附录 D（破坏性变更）**：
  - 全部作为 `library` 档的判断类规则，不映射 PublicApiAnalyzers 的 RS 诊断，因为它们不在 SDK 中，`check` 无法校验；
  - fdg-review 评审库的改动时，以用户指定的基线为准，默认是当前分支与默认分支的 merge-base，按附录 D 逐条对照；
  - 规则 notes 中说明，PublicApiAnalyzers（`/fdg-setup` 可选启用）能帮助发现公开 API 的变化。
- **Stop 遇到需要破坏性修改的诊断时**：
  - 现在：本轮改动行上的诊断一律打回。
  - 第二期改为：映射为 `autofix: breaking` 的诊断，如果所在的声明在本轮开始时已经存在，即已有的 API，Stop 不打回。这类问题列在报告末尾，并注明 “existing API: do not change it to fix this; tell the user”。
  - 只有本轮新增的声明才按原规则打回。
  - 判断“声明是否已存在”：在本轮开始时的文件内容中，用相同的符号名和种类查找。
  - 这项改动属于第 2 节的例外条款，在第一个带来大量此类诊断的章节（第 4 章或第 5 章）中一起完成，并配测试。
